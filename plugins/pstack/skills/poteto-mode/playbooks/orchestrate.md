### Orchestrate

**You own the program, never the code. Author briefs, drain the queue, keep the frontier green, decide.** For a whole project handed to one standing coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, the human checking in twice a day instead of every five minutes. One task driven to a predicate is Autonomous run. One ambitious run needing a bespoke workflow is figure-it-out. Route here when the work outlives any single agent. Work one agent could finish inside the session's budget is not a program.

Ceremony must scale with the program. On cheap near-identical units, collapse it as each section directs.

Three rules carry the rest.

- Completions are queue events, not interrupts.
- Every spawn and every resume carries the standing orders verbatim.
- The brief is the product. A vague brief fails quietly, because a worker cannot ask you a question.

#### Roles and placement

- **Coordinator (this chat).** Local. Frames, authors briefs, drains the completion queue, owns the human report, makes judgment calls. It never authors or edits code. Conflicted merges, restacks, and code changes are always tasks. Mechanically landing a verified unit (fast-forward or clean cherry-pick of a worker's commit, then push) is bookkeeping the coordinator may do itself on repos where local git is cheap. Queueing finished work behind an idle stacker is how a deadline harvests nothing. The loop is agentic end to end. Agents are spawned, resumed, and drained only through the Task tool. State reads and writes go through `bd` at drain points. `bd` never spawns, waits, or wakes anything.
- **Sub-coordinator.** Always local, durable, one per track, and only when the program exceeds what one coordinator's drains can manage. A track the coordinator can drain itself needs no middle layer. Each nested layer re-pays a full orientation preamble, and a blocking sub-coordinator hides its children while the parent idles. Owns its track's unit beads (label `track:<name>`), authors its workers' briefs, spawns its own workers and verifiers (nesting works to depth 3, and a nested spawn has the full Task schema including `environment`). Rolls up aggregates at wave boundaries. Never forwards raw child reports. Cap in-flight children at what one drain can process, roughly ten, as a rolling window. Never as blocking batches, which cost the slowest child of every batch.
- **Worker / verifier.** Always `environment: "cloud"` unless the task needs this machine: `control-ui` or `control-cli` runtime verification (from `cursor-team-kit`). Reading local transcripts under `agent-transcripts/`. Simulators and local IDE state. Auth that exists only here. Cloud agents cannot reach the local beads database, so their briefs inline what they need or point at repo paths. Prefer fewer, broader workers. One writer per worktree or branch (principle-separate-before-serializing-shared-state). Run a unit's verifier on a different model family from its worker.

Depth stays at coordinator, track, worker. Author the track decomposition per project (build, landing, and verification are common cuts, not a required shape). Hard-coded swarm trees were tried and parked as too rigid.

#### Program state in beads

The program state lives in the beads database at `BEADS_DIR`. Each agent writes only its own comments and metadata keys. Owners publish facts, and readers aggregate at read time. `bd` serializes writes, so concurrent writers need no lock. `bd help <command>` gives the exact flags.

- **The epic.** One epic holds the program. Its description holds the objective, and its acceptance holds the countable done predicate. Create it with `bd create "<program>" -t epic --description "<objective>" --acceptance "<predicate>"`. The epic and its children are the durable PR and issue record.
- **Units.** Each unit is a child bead of the epic, and its description is the brief. Create it with `bd create "<unit>" --parent <epic> --labels track:<name> --body-file <brief>`. Record the branch, the PR, and the head SHA as metadata (`bd update <id> --set-metadata branch=<branch> --set-metadata pr=<n> --set-metadata sha=<sha>`). Link the PR or issue with `--external-ref`. Record a state finer than the bead status with `bd set-state <id> stage=<value>`.
- **Writers and claims.** A unit has one worker for its life. A fix after `verifier-failed` is a new unit. Before you spawn a unit's worker, claim the unit bead under the worker's actor name (`BEADS_ACTOR=worker-<unit> bd update <unit> --claim`). The claim removes the unit from `bd ready`. The claim exits 1 if another actor holds the unit, and then you do not spawn. A local worker sets `BEADS_ACTOR=worker-<unit>` on each `bd` call. A verifier does not claim the unit. `bd close` refuses a claimed bead unless the actor holds the claim, so close a unit as its worker (`BEADS_ACTOR=worker-<unit> bd close <unit> --reason <reason>`). Other writes from any actor succeed.
- **Stages.** The stage tells a drain which units wait for it. A worker ends with its report and `bd set-state <unit> stage=built`. A verifier ends with its verdict record and `bd set-state <unit> stage=checked`, whatever the verdict is. A drain then moves the unit to a different stage, per Queue and drain.
- **Standing orders.** Each order is a decision bead under the epic, with one constraint (model policy, stack shape and count, verification bar, forbidden paths, escalation policy). Create it with `bd create "<order>" -t decision --parent <epic>`. To change an order, create the new decision bead and run `bd supersede <old> --with <new>`. `bd list --parent <epic> -t decision` lists the open orders. Paste their titles verbatim into every spawn and every resume. Directives decay across resumes, and each dropped one costs a human turn. When you catch yourself restating an instruction, create its decision bead before you act (principle-encode-lessons-in-structure).
- **Counts.** Compute them at read time. Do not keep a status file. `bd list --parent <epic> -t task --all --flat` lists the units with their status, one line for each unit. Without `--flat`, the total also counts the epic. `bd ready --parent <epic> -t task` lists the unclaimed units that have no open blocker. The `-t task` filter keeps the decision beads and the stack beads out of both lists. `bd blocked --parent <epic>` lists the blocked children of the epic.
- **Verdicts, gates, and the frontier.** A verdict is a record on its unit bead, per Verification. A human gate is a gate bead, per Escalation. The frontier is computed each time and never stored, per Stack safety.
- **The trail.** The show-me-your-work trail stays in the work directory.

#### The brief

Your prompts to agents are your only product, and a sloppy brief compounds into slop across the whole tree. Every spawn carries all of it. A field you cannot fill is a unit you have not scoped yet.

```
GOAL         one sentence, the outcome, executable by a stranger with no chat access
SCOPE        paths this unit may write; paths it may not; its exclusive worktree or branch
CONTEXT      pointers to files and PRs; upstream reports pasted in full when this unit
             depends on them, because workers cannot see siblings
ACCEPTANCE   checkable criteria, one per line
VERIFY       exact commands or the control-skill path, plus known gotchas
TIMEBOX      rough cap on runtime; on expiry, return partial findings and stop rather than run on
FORBIDDEN    no gt, no rebase, no force-push, no fixes outside scope, plus unit-specific bans
REPORT       status, branch, head SHA, PRs, verdict, what you actually ran, deviations,
             suggested follow-ups. Local: with BEADS_ACTOR=worker-<unit> (or verifier-<unit>),
             run bd comment <unit> --file <report>, then bd set-state <unit> stage=built
             (worker) or stage=checked (verifier). Cloud: return it as your final message
STANDING     <titles of the open decision beads under the epic, pasted verbatim>
```

Size the brief to the unit. A one-command unit gets the template collapsed to a paragraph that still names goal, scope, the verify command, the report shape, and the stage write. A 4KB scaffold around a two-line edit costs more to write and obey than the edit. A local spawn may name the epic ID instead of pasting the standing orders, because a local worker can run `bd list --parent <epic> -t decision` itself. Verbatim paste is for cloud spawns and every resume.

A sub-coordinator brief adds its track boundary and unit list, its spawn budget with the cloud default and the local exception list, the drain protocol from Queue and drain, and the rollup format (per child: unit bead ID, status, PR, head SHA, verdict, one line, plus track status and frontier delta).

A dependency is a context relay, not just ordering. Undeclared upstream context makes the worker guess. Create a dependent unit's bead only after its upstream reports arrive, because its brief pastes them. Then `bd ready` never lists a unit whose upstream context is missing. Missing fields are a refuse-to-spawn condition. Audit one sampled worker brief per sub-coordinator per wave, concurrently with the wave it samples, never as a gate in front of it. A failing brief stops that track and fixes the sub-coordinator's instructions, not just the worker, because brief quality decays late in a run. Never resume-chain a brief. Respawn fresh with consolidated scope.

#### Steps

1. **Frame.** State the done predicate as something countable ("all 126 units merged, each with a current verdict of `unit-test-verified` or better"). Quantify scope: units, rough effort, expected stacks, and the wall-clock budget. If one agent could finish inside that budget, stop here and run Autonomous run instead. Collapsing must not depend on another document being present. It means do the work directly in this session, plain workers where they help, verification inline, landing as you go, and none of the epic, standing-order, or pilot machinery below. Schedule landing against the budget. By roughly 70% of it, stop spawning and land what is verified. Name the tracks per project. A contested decomposition or one-way door goes through the arena skill before the pilot. Present the framing once. Reversible prep proceeds without waiting.
2. **Set up the program.** Create the epic. Create one decision bead for each standing order before any spawn. Open the trail via the show-me-your-work skill. Compute the frontier from the existing PRs, per Stack safety.
3. **Pilot.** Push one unit through the whole path: brief, worker, verification, stack entry, verdict record, merge. The pilot exists to falsify the brief template, the verify recipe, and the unit size while that costs one agent instead of fifty. Fix the contract from pilot evidence before any fan-out. Scale the pilot to the unit. On programs of near-identical cheap units, the first unit is the pilot, run as a normal unit with its verify command inline, and fan-out starts the moment it lands. The dedicated pilot pipeline (separate verifier agent, audit gate) is for expensive or novel unit shapes, not for clone-units where a serialized pilot has nothing to falsify.
4. **Scale.** Spawn a rolling window of workers up to the in-flight cap, refilling as children finish. Blocking batches pay the slowest child of every batch. Spawn track sub-coordinators only past the one-drain threshold in Roles. Recompute ready work (`bd ready --parent <epic> -t task`) after each drain. Relay upstream reports into downstream briefs. Keep sibling communication upward only. The sampled brief audit runs alongside the wave it samples and stops the next refill on failure, not the current one.
5. **Drain.** Run the queue discipline below at every drain point.
6. **Land.** Landing is continuous, never a terminal phase. Integration starts with the first verified unit and runs alongside the remaining waves. On heavy repos the stacker is a standing role from wave one, integrating as units verify. On repos where local git is cheap, the coordinator lands verified units itself per Roles. Keep the frontier green before upper-stack work. Stack safety governs. Recompute the frontier on each merge and each reported new head SHA.
7. **Close.** Drain the queue a final time. Close every unit bead as its worker, per Writers and claims, with a terminal reason (done, abandoned, or zombie-reconciled). Close each open stack bead as its stacker, and each open decision bead. `bd close <epic>` exits 1 while a child is open. Confirm the predicate on the real artifact. Confirm that every landed PR has a verdict for its current head SHA. Audit the trail per show-me-your-work, including its cross-model review. Encode recurring corrections as decision beads or in the brief template. Then close the epic. Do not delete the epic or its children. They are the postmortem.

#### Queue and drain

- Each unit bead is the completion queue for its unit. Before it exits, a local worker or verifier writes its report as a comment on its unit bead and then sets the stage of the unit, per Stages. A cloud agent cannot reach the beads database. On its completion notification, you write its report to its unit bead (`bd comment <unit> --file <report>`) and set the stage. Then return to what you were doing. Never deep-review inline. A completion that needs review gets a verifier, per Verification. Never review a diff inside a drain.
- Drain in batches at four points: the end of a critical section, a track rollup, a frontier watcher wake (arm it via the loop skill, with a long heartbeat fallback), and before a human report. Begin each batch with `bd list --parent <epic> -t task --label-any stage:built,stage:checked --flat`. It lists each unit whose agent reported after a drain last moved the unit. Arrivals during a drain wait for the next one.
- Critical sections you finish first: authoring a brief, a stack operation, a conflict decision, writing a gate, writing a verdict record, recomputing the frontier.
- Each drain classifies every listed unit (landed, needs-verify, failed, zombie, noise). It writes the class as the stage of the unit (`bd set-state <unit> stage=<class>`), so the next drain does not list the unit again. It writes the details with `bd update` and `bd comment`, counts the units again, and then spawns the next wave in one message.
- Account for every spawned child at its track's rollup: arrived, respawned, or its scope explicitly absorbed. Silently redoing a missing child's work hides both the wasted spend and the coverage gap its result existed to close.
- A drain turn ends with three lines: the unit counts against the states, what changed, and the open gates of the program (`bd blocked --parent <epic>`, per Escalation). Detail lives in the unit beads. The full reply contract applies at checkpoints and close.

#### Stack safety

- The frontier is a computed object, never narrative, and it is never stored. It holds the ordered PR list, the branch names, the head SHAs, and the lowest unmerged PR. Recompute it after every merge and stack mutation from `gt --no-interactive log short --stack --reverse` plus `gh pr view` for each branch. The `--reverse` flag prints trunk first, so the list reads bottom-up and the first unmerged PR in it is the lowest. Use `gt`, not the GitHub base refs, because the base refs drift mid-restack while gt tracking is authoritative. Resolve it where gt knows the stack, normally the stacker's clone. A checkout whose gt metadata never saw the submits reports no PRs. Treat that as an error, not as an empty stack.
- Exactly one stacker per stack may run `gt`, serialized within its stack. Each stack has one chore bead under the epic (`-t chore`). Before you spawn the stacker of a stack, claim the stack bead under the actor name `stacker-<stack>` (`BEADS_ACTOR=stacker-<stack> bd update <stack> --claim`). If the claim exits 1, another actor holds the stack, so do not spawn. A replacement for a dead stacker uses the same actor name, so its claim succeeds with no reclaim. Close the stack bead as `stacker-<stack>` when the last PR of the stack merges. Restacks run in cloud. A local restack at this scale takes the laptop down.
- Workers never rebase and never run `gt`. Babysitters follow `playbooks/babysit.md`, one per stack, scoped to the head SHAs in their brief. A new head SHA ends that scope. They report conflicts to the stacker rather than restacking.
- PR closes and retargets go through the stacker only. Closing a base PR orphans every chain above it. Merges and stack surgery are units with briefs like any other.
- One retro watcher follows merged PRs for reverts, post-merge CI breaks, and orphaned follow-ups.

#### Verification

Scale verification to the unit. When VERIFY is a single cheap command, the worker runs it and reports the output, and the coordinator spot-checks receipts. A dedicated verifier agent (on a different model family than the worker) is for units whose verification is expensive, judgment-laden, or high-blast-radius. A verifier agent whose entire product would be rerunning one command is ceremony, not verification.

Record each verdict on its unit bead, keyed by PR number plus head SHA. Add a comment with `bd comment <unit> "verdict=<v> pr=<n> sha=<sha> verifier=<agent> evidence=<pointer>"`. Then set the metadata with `bd update <unit> --set-metadata verdict=<v> --set-metadata verdict_sha=<sha>`. The verdicts are `live-ui-verified | unit-test-verified | type-check-only | verifier-blocked | verifier-failed`. bd stores any value, so check the value against these five names before you write it. A reader treats any other value as no verdict. To find such values, compare `bd list --parent <epic> -t task --all --flat --has-metadata-key verdict` with the five lists from `--metadata-field verdict=<v>`. A unit that is only in the first list needs a new verdict. To check a verdict, compare `verdict_sha` with the PR's head SHA from `gh pr view <n> --json headRefOid`. A different SHA means the PR has no current verdict. CI green is an input to a verdict, not a verdict. Behavioral work needs better than `type-check-only`. `verifier-blocked` is not a pass. Respawn when the environment heals. `verifier-failed` gets a fix unit, not a re-verify. A worker may self-report. A verifier overrides it with a new record on the same key. A new head SHA voids the verdict, so re-verify after restack. The verdict records answer "was this verified", not memory and not the transcript.

A unit is not done until its output is externalized the moment it lands, never batched to the end of the run. A worker pushes its branch, a verifier writes its verdict record, and the reports land on the unit beads. Work that exists only on one VM when that VM dies was never done.

#### Liveness and failure

- Never resume an agent to check on it. A resume restarts an idle agent. Probe read-only: the unit beads (`bd show <unit>`), `gh`, pushed branches, the cloud agent's status in the Cursor dashboard. Transcript mtime is not liveness.
- A silent death gets a synthetic postmortem comment on its unit bead (failure mode, last evidence, options). Then set `bd set-state <unit> stage=built` for the dead worker, so the next drain lists the unit and classifies it. Replan on evidence as it arrives. Never wait for full quiescence.
- Retry by mode: cap-hit or oom, respawn with smaller scope. Network-drop, retry as-is. Tool-error, retry on a different model. Unknown, retry once. Two retries, then abandon the unit and replan around it.
- A zombie that returns hours late reconciles against the current frontier and the verdict records on its unit bead before anything is accepted. Salvage unique findings through a fresh unit, never a blind merge.
- When continued spawning would produce garbage tree-wide (bad upstream output, broken acceptance, dead infra), create a stop line as a decision bead under the epic (`bd create "STOP: <cause>" -t decision --parent <epic>`). Every spawn then carries it with the standing orders. Let in-flight work finish, fix the cause, and close the stop bead to clear it.
- Bound your own infra retries the same way you bound a child's. After a few consecutive tool aborts, stop retrying. Write a terminal handoff as a comment on the epic (what is done, where it lives, the exact command to resume) and end the run.
- After a Cursor restart: local agents are dead, cloud work is not. Re-read the epic and its open decision beads, run `bd list --parent <epic>`, recompute the frontier, reattach cloud work by PR and branch rather than agent id, respawn one sub-coordinator per track from its bead description plus current state, drain, resume. Respawn a dead worker under its old actor name (`worker-<unit>`). The claim on the unit bead still holds for that name, so the claim before the respawn succeeds with no reclaim.
- Do not run `bd reclaim` without `--id`. No agent sends `bd heartbeat`, so every claim lease expires 5 minutes after its claim. A bare `bd reclaim` then reopens every claimed unit and stack bead, and puts the units back into ready work.

#### Escalation

Reaches the human, batched into the next report rather than per item: irreversible actions (force-push to shared branches, deploys, deletions, closing someone else's PR), genuine product or preference calls no experiment settles, a standing order that contradicts observed reality, a program-level dead end that survived a replan. Before you ask, park each one as a human gate on a bead under the epic with `bd gate create --blocks <bead> --reason "<question, options, default on no answer>"`, and route work around it. `bd gate list` shows the open gates of the whole database, not only of this program. `bd blocked --parent <epic>` lists the beads of the program that a gate blocks, with the gate ID. `bd gate show <gate>` shows the question. `bd gate resolve <gate> --reason "<answer>"` clears the gate and keeps the human's answer as its close reason. Without `--reason`, bd drops the answer.

Never reaches the human: frontier nudges, restack mechanics, retries, CI flake triage, review-thread triage, format fixes, scope the brief already forbids (refuse and continue), and "should I keep going". When in doubt, act and log.

Mid-run discoveries fix only what blocks the frontier. Everything else parks in follow-ups. Create each follow-up outside the epic with `bd create "<follow-up>" --deps discovered-from:<unit>`, so it does not count as a unit and does not show in ready work. At this fan-out a small scope leak multiplies into PRs nobody asked for.

**Reply:** at checkpoints and close: the predicate and the count against it from `bd list --parent <epic> -t task --all --flat`, tracks and what each landed, the frontier (PR list plus SHAs), a verdicts summary from the `verdict` metadata, what was abandoned and why, gates awaiting the human from `bd blocked --parent <epic>`, each with its question from `bd gate show <gate>` (the only asks), the epic ID, and the trail path. Numbers from `bd`, not narrative. Include PR links.
